# TamarinOpenXrAndroidBindings

Java bindings for OpenXR on Android (initially targeting the Meta Quest headset) and desktop (Windows and Linux).

## Overview

This library provides Java bindings for the OpenXR API, allowing Java applications to interact with OpenXR-compatible VR/AR devices. The bindings use JNI (Java Native Interface) to call the native OpenXR functions from Java code.

The API is modelled on LWJGL's OpenXR bindings (structs with `malloc`/`calloc`/`MemoryStack` allocation, `XR10` static calls, etc.) and is the same on every platform, so the same OpenXR code can run on a standalone headset and on PCVR. It is primarily built for the [Tamarin](https://github.com/oneMillionWorlds/Tamarin) VR library but can be used on its own.

## Features

This includes the entire OpenXR API version 1.1.63 (the version of the OpenXR loader it depends on), including extensions, for the platforms and graphics APIs it supports: Android + OpenGL ES, and on desktop OpenGL on Windows (Win32) and Linux (Xlib, XCB, Wayland and EGL). It is a thin binding to c.

Every platform's structs and functions are in the (single) Java API; calling a function that isn't available on the platform the program is running on returns `XR_ERROR_FUNCTION_UNSUPPORTED`.

Only calls required by the Tamarin engine are tested but as all of the api is generated by code generation it is likely the rest works.

## Modules

| Artifact | What it is |
| --- | --- |
| `openxr-bindings-core` | The Java API (the same on every platform). Needs one of the below for the native library |
| `openxr-bindings-android` | The native library for Android (arm64-v8a) and the Android only parts (`AndroidThickC.initializeLoader`). The OpenXR loader comes transitively from Khronos' `org.khronos.openxr:openxr_loader_for_android` |
| `openxr-bindings-desktop` | The native library for Windows x64 and Linux x64, with the OpenXR loader statically linked into it |

Both native artifacts depend on `openxr-bindings-core`.

## Requirements

- Android: minSdk 26+, arm64-v8a
- Desktop: Windows x64 or Linux x64 (glibc), Java 11+ and an OpenXR runtime (e.g. SteamVR, Meta Quest Link, Monado)

To build from source:

- Android SDK (with `local.properties` pointing at it) and NDK
- CMake and a C/C++ compiler for this machine (for the desktop library; Visual Studio on Windows, gcc/clang plus the X11 headers, `libx11-dev`, on Linux). Without them pass `-PskipDesktopNatives`
- JDK 17 (Gradle 9 is provided by the wrapper)

## Installation

Add the library to your project's dependencies (see [Maven Central](https://central.sonatype.com/artifact/com.onemillionworlds.tamarin/openxr-bindings-core) for the latest version):

```gradle
dependencies {
    // on Android
    implementation 'com.onemillionworlds.tamarin:openxr-bindings-android:<version>'
    // on desktop
    implementation 'com.onemillionworlds.tamarin:openxr-bindings-desktop:<version>'
}
```

Code that is shared between platforms only needs `openxr-bindings-core`.

On Android call `AndroidThickC.initializeLoader(activity)` before any other OpenXR call. On desktop nothing is needed; the native library is extracted from the jar and loaded when first used.

## Building from Source

1. Clone the repository:
   ```
   git clone https://github.com/oneMillionWorlds/TamarinOpenXrAndroidBindings.git
   ```

2. Build the library (this also runs the code generation and tests):
   ```
   ./gradlew build
   ```
   This builds the desktop native library for the machine it is run on only. `-PskipDesktopNatives` skips it (e.g. without a C compiler)

3. The libraries will be in `openxr-bindings-core/build/libs/`, `openxr-bindings-android/build/outputs/aar/` and `openxr-bindings-desktop/build/libs/`.

### Development Tasks

#### Code generation

Almost all of the Java API (`XR10`, the structs, enums and handles) and the JNI C wrapper are generated during the build from the OpenXR registry (`xr.xml`). It isn't checked in: it is downloaded from the matching [OpenXR-SDK-Source](https://github.com/KhronosGroup/OpenXR-SDK-Source) release tag, so it is always the same version as the loader (`openxr-loader` in `gradle/libs.versions.toml`). The build therefore needs network access to GitHub. The generator lives in `buildSrc` and is run by the `parseOpenXrFile` task, writing the Java into `openxr-bindings-core/src/main/generated` and the C into `native/generated` (neither checked in, never edit by hand). To only regenerate:

```
./gradlew :openxr-bindings-core:parseOpenXrFile
```

#### Running tests

`./gradlew build` runs the library's tests (including, on desktop, tests that call the real native library). The code generator's own unit tests live in `buildSrc` and have to be run separately:

```
./gradlew -p buildSrc test
```

CI runs both (and the desktop tests on Windows too).

#### Updating Reference Struct Files

The project includes tests that compare generated struct files with reference versions to ensure consistency. When you make changes to the struct generation code and want to accept the new generated files as the reference:

```
./gradlew :openxr-bindings-core:updateReferenceStructs
```

This task will update only existing reference struct files with their corresponding generated versions. It will not create new reference files. Only run this task when you've verified that the changes to the generated files are correct and should become the new reference standard.

Note: Only a small subset of generated files are used as references in tests. This task preserves that subset and only updates those files that already exist as references.

## Implementation Details

The library uses JNI to bridge between Java and the native OpenXR API. The implementation follows these steps:

1. The code generator reads `xr.xml` and generates the Java API and the C JNI wrapper
2. JNI headers are generated from the Java classes (`javac -h`)
3. C implementation forwards calls to the OpenXR API (extension functions are looked up via `xrGetInstanceProcAddr` after instance creation)
4. Results are written into native memory owned by the Java structs/buffers and an `XrResult` is returned

See README_DEEP.md for more detail.
